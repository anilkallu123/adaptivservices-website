Migrating to
Oracle Database@AWS:
Methodology and Gotchas

Infrastructure provisioned. Now the hard part: getting your data there. Four phases from AWR analysis to live cutover, and the things that break silently if you skip the discovery work.

Parts 1–3 covered what Oracle Database@AWS is, when to use it, and how to provision it with Terraform. This article covers the migration itself, how you move an existing Oracle workload onto ODB without a data loss event, an unexpected outage, or a performance regression that your AWR didn't predict.

The methodology has four phases. Discovery and Design are where migrations succeed or fail. Most teams understand that intellectually but still compress them in practice. We'll cover what that compression costs.

Phase 1, Discovery

01
Discovery
Typical duration: 2–4 weeks

Discovery produces four artefacts: an AWR analysis, a schema inventory, a licensing audit, and a network topology map. All four are required inputs to Design. Missing any one of them produces a Design phase that will need to revisit Discovery mid-execution.

  • AWR analysis, baseline performance profile: top SQL by elapsed time and CPU, I/O pattern (reads vs writes, sequential vs random), wait event profile, and smart scan eligibility. The AWR baseline is also your post-migration acceptance criterion, if smart scan utilisation on ODB doesn't exceed the baseline, something is wrong with the storage cell configuration or AZ alignment.
  • Schema inventory, all schemas, object counts, data volumes, and dependencies (DB links, external tables, directory objects, scheduler jobs, DBMS_SCHEDULER chains). External dependencies, anything that reaches outside the database, must be resolved before cutover.
  • Licensing audit, which Oracle options are in use (Partitioning, Advanced Compression, Diagnostics Pack, Tuning Pack, etc.), which are licensed, and what the licensing model will be on ODB (LicenseIncluded or BYOL). The audit must be done now, not at contract renewal time.
  • Network topology, what connects to the database (application tiers, ETL servers, reporting tools, DB links to other databases), where they're deployed, and whether they'll be in the same AZ as the ODB network after migration.

Phase 2, Design

02
Design
Typical duration: 2–3 weeks

Design produces the ODB sizing specification, AZ alignment plan, TDE key management strategy, cutover approach, and rollback plan.

  • ODB sizing, VM cluster compute count (number of RAC nodes), CPU core count (OCPU, billed per enabled core), data storage in TB. Size from AWR peak workload, not average. For Exadata shapes, minimum data storage is 2TB, scalable in 2TB increments.
  • AZ alignment, confirm the physical AZ ID for the ODB network matches the AZ where the application tier will live. If the app tier is being migrated to AWS simultaneously, the AZ alignment must be coordinated across both workstreams.
  • TDE key management, decide between AWS KMS-managed TDE keys or Oracle Wallet-managed keys. KMS integration is recommended for enterprises with existing AWS KMS governance, it means TDE key rotation follows the same process as all other AWS key management.
  • Cutover approach, Data Pump or GoldenGate. This decision drives the cutover window requirement. See below.
  • Rollback plan, ODB provisioning is not reversible quickly. Define the rollback point (usually: application connection strings still pointing at source), the rollback trigger conditions (error rate, latency threshold, data integrity check failure), and the team responsible for calling it.

Data Pump vs GoldenGate, Making the Call

This is the decision that most directly determines your cutover risk and your maintenance window requirement.

FactorData PumpGoldenGate CDC
Cutover windowProportional to data volume, plan 2–4 hours per TB at parallel=4Near-zero, cutover is a connection string flip after sync

GoldenGate prerequisite that burns teams

If you're using GoldenGate CDC, supplemental logging must be enabled on the source database before the initial data load begins, not at cutover time. Enabling it after the initial load means the Replicat process cannot reconstruct the full change history for rows that changed between the initial load and the CDC start point. Enable ALTER DATABASE ADD SUPPLEMENTAL LOG DATA and schema-level supplemental logging during Discovery, not Design. It has near-zero performance impact on OLTP workloads.

Phase 3, Delivery

03
Delivery
Typical duration: 3–6 weeks

Delivery is the Terraform provisioning phase. Following the two-phase pattern from Part 3:

  • Phase 1 Terraform apply, ODB network, Exadata infrastructure (4–6h), VM cluster, KMS keys. Validate network peering connectivity from the application VPC before proceeding.
  • Phase 2 Terraform apply, DB Home, CDB, PDB(s). Run schema creation scripts and verify connectivity from application hosts.
  • Performance baseline run, run the AWR workload against the empty ODB target to validate smart scan is functioning (check V$SYSSTAT for cell physical IO interconnect bytes returned by smart scan). Non-zero value confirms smart scan is active.
  • If using GoldenGate: configure Extract on source, run initial data load, configure Replicat on ODB, verify lag is below threshold before declaring readiness for cutover.

Phase 4, Migration and Cutover

04
Migration & Cutover
Planned window or near-zero (GoldenGate)

The cutover sequence for Data Pump migration:

  • Freeze application writes (put application in maintenance mode or redirect to read-only fallback)
  • Run final incremental Data Pump export of changed data since the initial load
  • Import incremental dump to ODB target
  • Run integrity check, row counts per table, sequence current values, constraint violations
  • Update application connection strings to ODB endpoint
  • Smoke test against ODB, verify application writes and reads
  • Remove maintenance mode
  • Monitor AWR on ODB for first 24 hours, compare to baseline profile

For GoldenGate: the cutover is a connection string flip once GoldenGate lag is at zero. No maintenance window required. Post-cutover, run GoldenGate reverse replication back to the source for rollback readiness, drop it after 48 hours of stable operation.

"The AWR comparison after go-live is not a formality. Smart scan utilisation, I/O wait profile, and top SQL elapsed time should all match or improve vs the source baseline. A regression in any of these signals a configuration problem, not a performance characteristic of ODB."

What Breaks Silently

These are the issues that don't produce loud errors during cutover, they surface 48–72 hours later in production.

  • DB links to non-migrated schemas, if the migrated schema has DB links to databases that haven't been updated with the new ODB endpoint, queries that traverse those links succeed during testing (the link target hasn't changed) and fail in production when the link target changes as part of a subsequent migration phase. Audit all DB links in Discovery.
  • Scheduler jobs with hardcoded hostnames, DBMS_SCHEDULER external jobs that reference the old hostname directly will continue to run against the old database after cutover. They won't fail immediately; they'll fail the first time they run after the old database is decommissioned.
  • Sequence cache exhaustion on partial load, if the initial Data Pump load is interrupted and restarted, sequence values may advance beyond the exported high watermark. Applications that depend on sequence continuity (audit trails, correlation IDs) will have gaps. Always export sequences with INCLUDE=SEQUENCE and validate high watermark alignment post-import.
  • Time zone misalignment, ODB default database time zone is UTC. Source databases in production environments often have regional time zone settings. TIMESTAMP WITH LOCAL TIME ZONE columns will store values correctly but display and compare differently if the application assumes a specific server time zone.

Post-Go-Live Validation

The migration is not complete at connection string flip. Run these validations during the first 24 hours:

  • AWR snapshot comparison, capture a 30-minute AWR snapshot on ODB under production load and compare elapsed time and I/O profile against the source baseline
  • Smart scan validation, confirm cell physical IO interconnect bytes returned by smart scan is non-zero and proportional to expected workload
  • Data Guard lag, if Active Data Guard standby is configured, verify lag is within RPO threshold
  • Application error rate, compare application error logs pre and post cutover; any new ORA- errors require immediate investigation
  • Connection pool behaviour, verify connection pool is connecting to ODB and not caching stale connections to the old database endpoint
