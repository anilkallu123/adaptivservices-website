The architectural split in Oracle Database@AWS, AWS-managed infrastructure, Oracle-managed database layer, has a direct consequence for how you provision it. You can't do it with a single Terraform provider. You need the AWS provider for the ODB network and Exadata infrastructure, and you need the OCI provider for the DB Home, CDB, and PDBs. The handoff between them is the vm_cluster_ocid that Phase 1 outputs.

This two-phase pattern is how we productise ODB for consulting delivery. Instead of a bespoke infrastructure build for each customer, you get a parameterised Terraform call, swap the customer's variable values and the entire stack reproduces consistently. This article walks through both phases, the module structure, and the five gotchas that will cause a failed or rolled-back provisioning run if you don't handle them up front.

Phase 1, The AWS Layer

Phase 1 provisions everything that lives in your AWS account and is visible from the AWS console. The resources are:

  • ODB network (aws_odb_network), a dedicated network construct, AZ-pinned, that hosts the Exadata infrastructure. This is not a VPC; it's a separate networking primitive.
  • ODB network peering connection (aws_odb_network_peering_connection), connects the ODB network to your application VPC. Resources inside the app VPC route to Oracle via this peering. Prefix: odbpcx-.
  • Exadata infrastructure (aws_odb_cloud_exadata_infrastructure), the physical Exadata hardware reservation. This is the resource that takes 4–6 hours to create.
  • VM cluster (aws_odb_cloud_vm_cluster), the Oracle RAC cluster running on the Exadata infrastructure. This outputs the vm_cluster_ocid needed by Phase 2.
  • KMS key + Secrets Manager secret, TDE wallet encryption key and database credentials store, integrated with AWS-native key management.

main.tf, Phase 1 skeleton (AWS provider)
# Requires: hashicorp/aws >= 6.15, Terraform >= 1.12.0

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 6.15.0"
    }
  }
  required_version = ">= 1.12.0"
}

# ODB network, AZ-pinned to physical AZ ID, not AZ name
resource "aws_odb_network" "this" {
  display_name          = var.odb_network_name
  availability_zone_id  = var.az_id  # e.g. "use1-az4"
  client_subnet_cidr    = var.client_subnet_cidr
  backup_subnet_cidr    = var.backup_subnet_cidr
}

# Peering to application VPC
resource "aws_odb_network_peering_connection" "this" {
  odb_network_id     = aws_odb_network.this.id
  vpc_id             = var.app_vpc_id
  peer_network_cidrs = [var.app_vpc_cidr]
  vpc_route_table_id = var.app_route_table_id
}

# Exadata infrastructure, the 4-6h resource
resource "aws_odb_cloud_exadata_infrastructure" "this" {
  display_name          = var.exadata_infra_name
  availability_zone_id  = var.az_id
  shape                 = var.exadata_shape  # e.g. "Exadata.X9M"
  compute_count         = var.compute_count
  storage_count         = var.storage_count

  timeouts {
    create = "6h"  # ALWAYS set this, default is too short
    delete = "6h"
  }
}

# VM cluster, outputs vm_cluster_ocid for Phase 2
resource "aws_odb_cloud_vm_cluster" "this" {
  display_name                   = var.vm_cluster_name
  cloud_exadata_infrastructure_id = aws_odb_cloud_exadata_infrastructure.this.id
  odb_network_id                 = aws_odb_network.this.id
  cpu_core_count                 = var.cpu_core_count
  data_storage_size_in_tbs       = var.data_storage_tbs
  gi_version                     = var.gi_version
  grid_image_id                  = var.grid_image_ocid  # see gotcha #3, attribute is grid_image_id, not grid_image_ocid
  ssh_public_keys                = [var.ssh_public_key]
  license_model                  = var.license_model  # LicenseIncluded or BringYourOwnLicense
  kms_key_id                     = aws_kms_key.tde.arn
}

output "vm_cluster_ocid" {
  value = aws_odb_cloud_vm_cluster.this.ocid
}

Phase 2, The Oracle Layer

Phase 2 uses the OCI Terraform provider and takes the vm_cluster_ocid from Phase 1 as its entry point. It provisions the database software layer: DB Home (the Oracle Database software installation), CDB (Container Database), and one or more PDBs (Pluggable Databases).

The key insight here is the separation of concerns. Phase 1 provisions hardware and networking, things that change infrequently and are managed by AWS infrastructure teams. Phase 2 provisions database objects, things that change more frequently and are managed by DBAs or application teams. Keeping them in separate Terraform states means a database schema change or PDB addition doesn't require re-planning the Exadata infrastructure stack.

main.tf, Phase 2 skeleton (OCI provider)
# Phase 2 takes vm_cluster_ocid as input from Phase 1 output

terraform {
  required_providers {
    oci = {
      source  = "oracle/oci"
      version = ">= 5.0.0"
    }
  }
}

# DB Home, Oracle Database software installation on the VM cluster
resource "oci_database_db_home" "this" {
  vm_cluster_id = var.vm_cluster_ocid  # from Phase 1 output
  display_name  = var.db_home_name
  db_version    = var.db_version  # e.g. "19.21.0.0"
  source        = "VM_CLUSTER_NEW"

  database {
    db_name       = var.db_name
    pdb_name      = var.initial_pdb_name
    admin_password = var.db_admin_password
    db_workload   = "OLTP"
    character_set  = "AL32UTF8"
    ncharacter_set = "AL16UTF16"
    tde_wallet_password = var.tde_wallet_password
  }
}

# Additional PDB per application/tenant
resource "oci_database_pluggable_database" "app" {
  container_database_id = oci_database_db_home.this.database[0].id
  pdb_name              = var.app_pdb_name
  pdb_admin_password    = var.pdb_admin_password
  tde_wallet_password   = var.tde_wallet_password
  should_pdb_admin_account_be_locked = false
}

The Five Gotchas

These are the issues that will burn provisioning runs if you don't handle them before you run terraform apply.

1. AWS provider version pinning

The ODB resources require hashicorp/aws >= 6.15. This is a major version jump from 5.x, and it is not backward-compatible. Many enterprise Terraform codebases are pinned to 4.x or 5.x for stability. Upgrading the provider version for ODB while leaving other infrastructure on the old version requires either a separate Terraform workspace/state for ODB, or a full provider upgrade with regression testing across the existing codebase. Do not underestimate this, it's the most common delivery delay in ODB projects.

2. AZ pinning on physical AZ ID

The ODB network, app VPC subnets used for peering, and Exadata infrastructure must all be in the same physical AZ ID, not the same AZ name. AZ names are account-scoped aliases; the same physical AZ may have different names in different AWS accounts. Resolve the physical AZ ID before starting: aws ec2 describe-availability-zones --region <region>. Bake the AZ ID directly into your variable definitions, not the name.

AZ ID resolution command

aws ec2 describe-availability-zones --region us-east-1 --query 'AvailabilityZones[*].[ZoneName,ZoneId]' --output table, run this in each AWS account that will host ODB resources. The ZoneId (e.g., use1-az4) is what goes into your Terraform variables, not the ZoneName.

3. grid_image_ocid has no enumeration API

The grid_image_ocid parameter on the VM cluster resource specifies the Oracle Grid Infrastructure image version. There is currently no AWS API to list valid values for your region and shape combination. The only reliable method is to retrieve it from an existing ODB VM cluster in the same region: aws odb describe-cloud-vm-clusters --region <region>. Document the OCID in your module's variable definitions with a clear comment, it changes with Grid Infrastructure patch releases and will cause a forced replacement if updated without a planned maintenance window.

4. Timeout on Exadata infrastructure create

Always set timeouts { create = "6h" } on aws_odb_cloud_exadata_infrastructure. The Terraform provider's default timeout is shorter than the actual provisioning time in some regions. A timeout during infrastructure creation leaves a partially provisioned resource in a state that requires Oracle support to clean up, it doesn't roll back cleanly. The 6-hour timeout is the safe value; it simply lets the provider wait without error.

5. State separation between phases

Keep Phase 1 and Phase 2 in separate Terraform state files, either different workspaces or different backend paths. Phase 1 (Exadata infrastructure) has a 4–6 hour provisioning cycle and should never be in the same plan-apply cycle as Phase 2 (DB Home, PDB). If you combine them, a PDB addition or DB Home change will trigger a plan that includes the Exadata infrastructure in scope, creating risk of accidental destruction of the physical layer when you intended to only change the database software layer.

"The two-phase pattern is how you turn ODB from a bespoke infrastructure build into a repeatable, productised delivery. Each customer gets a parameterised call, not a hand-built environment."

Module Structure for Consulting Delivery

For consulting delivery, we structure ODB as two reusable Terraform modules, one per phase, with a thin customer-specific root module that wires them together via output/variable chaining.

Module structure, consulting delivery pattern
modules/oracle-db-aws-infra/ ← Phase 1 module
├── main.tf (ODB network, Exadata infra, VM cluster, KMS)
├── variables.tf (az_id, shape, cpu_count, storage_tbs, ...)
└── outputs.tf (vm_cluster_ocid, odb_network_id, peering_id)

modules/oracle-db-aws-database/ ← Phase 2 module
├── main.tf (DB Home, CDB, PDB)
├── variables.tf (vm_cluster_ocid, db_version, pdb_names, ...)
└── outputs.tf (db_home_id, pdb_connection_strings)

customers/acme-corp/ ← customer root module
├── main.tf (calls both modules, wires outputs → inputs)
├── terraform.tfvars (customer-specific values)
└── backend.tf (separate state per phase)

The module library is published to GitHub under anilkallu123/terraform-aws-oracle-database, open source, versioned with release-please, with terraform-docs generated reference. Companion modules for Azure and GCP follow the same two-phase pattern.

CI/CD Considerations

Running ODB provisioning in CI has one significant constraint: the 4–6 hour Exadata infrastructure creation time. This is not a pipeline step you run on every PR. The practical pattern:

  • Phase 1 (infra) runs on a separate, manually-triggered pipeline, or a scheduled job during approved maintenance windows. It writes state to a shared remote backend.
  • Phase 2 (database) runs on a standard PR-gated pipeline. It reads the Phase 1 state as a remote state data source and plans only the database layer changes.
  • Plan output for Phase 2 must explicitly show that no Phase 1 resources are in scope before merge approval is granted.
