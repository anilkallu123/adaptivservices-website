Oracle Database@AWS:
What It Actually Is
(And What It Isn't)

It's not RDS for Oracle. It's not Oracle on EC2. It's genuine Exadata hardware running inside an AWS Availability Zone, managed by Oracle, billed through AWS. Here's what that distinction means in practice.

Every conversation I've had about Oracle Database@AWS starts with the same misconception: people assume it's a managed Oracle service on top of AWS infrastructure, like RDS for Oracle, but newer. It isn't. The architecture is fundamentally different, and getting that distinction wrong leads to bad sizing decisions, wrong cost models, and migration plans that don't hold up.

This is Part 1 of a six-part series on Oracle Database@AWS (ODB). We'll cover the full picture, from what it is and when to use it, through Terraform delivery, migration methodology, and licensing. This first article is about the architecture itself. Get this right and everything else follows.

What ODB Is Not

Let's clear the deck first.

Oracle Database@AWS is not Amazon RDS for Oracle. RDS for Oracle runs Oracle Database software on AWS-managed EC2 instances. You get automated backups, patching, and Multi-AZ failover, but you're running Oracle Standard Edition 2 or Enterprise Edition on virtualised compute. No Exadata smart scan. No Real Application Clusters (RAC). No Oracle Maximum Availability Architecture (MAA) guarantees. Storage is EBS, not Exadata Intelligent Storage Cells. It's Oracle on AWS infrastructure, managed by AWS.

ODB is not Oracle on EC2 either. That's a self-managed deployment, you provision EC2 instances, install the Oracle Database software, configure ASM, manage patching yourself. Full control, full operational burden.

And ODB is not Oracle Cloud Infrastructure. It's not a cross-cloud peering arrangement where your application in AWS connects to a database in OCI over Oracle Interconnect. The database physically runs inside an AWS Availability Zone.

The one-sentence definition

Oracle Database@AWS is genuine Oracle Exadata hardware, physically located inside an AWS Availability Zone, running inside an OCI child site that Oracle manages, billed jointly through your AWS console.

The Architecture

To understand ODB, you need to understand what "OCI child site" means in an AWS AZ. Oracle physically colocates Exadata infrastructure inside AWS data centres. That hardware runs an isolated OCI control plane, Oracle manages it, Oracle patches it, Oracle is responsible for its availability. From the customer's perspective, it appears in the AWS console as a set of resources under the odb service namespace.

The networking model is what makes this work without public internet exposure. Your application VPC in AWS connects to the ODB network via an ODB network peering connection, a dedicated construct with the odbpcx- prefix, distinct from standard VPC peering. Traffic between your application tier and the Oracle database travels over this peering at sub-millisecond latency, entirely within the AWS AZ boundary.

There are two layers to every ODB deployment, and they use different tooling. The AWS layer, ODB network, Exadata infrastructure, VM cluster, is provisioned via the AWS Terraform provider (version >= 6.15). The Oracle layer, DB Home, CDB, PDB, is provisioned via the OCI Terraform provider, using the vm_cluster_ocid that the AWS layer outputs. This two-phase architecture is intentional and consequential. We cover it in detail in Part 3.

Why Exadata Matters Here

The reason this distinction matters is that Exadata is not just faster Oracle on better hardware. The Exadata architecture offloads SQL processing to the storage layer, the Intelligent Storage Cells run a subset of the SQL execution plan directly against the raw blocks, before data is sent to the database nodes. This is called smart scan, and for analytical queries, full-table scans, and large aggregations, it can reduce I/O by an order of magnitude.

You also get:

  • Real Application Clusters (RAC), active-active multi-node clustering with automatic workload distribution and node-level failover
  • Oracle Active Data Guard, real-time standby replication with read offload on the standby, forming the basis of Oracle's Platinum MAA tier
  • Transparent Data Encryption (TDE), hardware-accelerated encryption at the storage cell level, with keys managed in AWS KMS or Secrets Manager
  • Oracle Database Vault, Audit Vault, the full Enterprise Edition feature set, including all compliance-oriented capabilities required by healthcare and financial services regulations

None of these are available on RDS for Oracle. All of them are available on ODB, because the hardware is Exadata.

"For enterprises that can't replatform their Oracle workloads but can't run separate OCI tenancies, ODB changes the equation entirely. The Exadata estate moves inside AWS without leaving Oracle's operational model."

The Commercial Model

The billing model is one of ODB's most practically significant features for AWS-first enterprises. Oracle Database@AWS charges appear on the AWS bill. This means:

  • Oracle costs can be applied against existing AWS Enterprise Discount Programme (EDP) commitments, subject to agreement with AWS
  • Finance teams have one vendor relationship for cloud spend, not a separate Oracle Cloud invoice
  • AWS Cost Explorer, cost allocation tags, and chargeback models all work across ODB and native AWS services without custom reporting

The billing is joint, Oracle charges for the database software and managed service; AWS charges for the physical infrastructure. But from the customer's perspective, it comes through a single pane of glass.

License model options

LicenseIncluded, Oracle Database Enterprise Edition and Exadata software licensing are bundled into the hourly charge. No Oracle ULA or per-processor license required. Simpler to start, higher running cost.

BringYourOwnLicense (BYOL), you supply verified Oracle per-processor or ULA licensing. Lower running cost, but requires Oracle License Management Services (LMS) verification. Most applicable to enterprises already on full-use Exadata licensing.

Regions and Availability

ODB reached general availability in July 2025 in us-east-1 and us-west-2. Since then, Oracle has added Frankfurt (eu-central-1), Tokyo (ap-northeast-1), and Ohio (us-east-2), with additional regions on the roadmap for APAC and additional EU coverage.

AZ pinning is strict, this is one of the most common configuration errors in early ODB deployments. The ODB network, all application VPC subnets that will peer with it, and the Exadata infrastructure must all be in the same physical AZ ID, not just the same AZ name. AZ names like us-east-1a are account-scoped; the physical AZ ID (e.g., use1-az4) is what matters. If these are misaligned, peering fails silently during provisioning, 4 to 6 hours into an infrastructure creation that then rolls back.

AZ pinning, the most common early mistake

Always resolve and confirm your physical AZ ID before you start. Use aws ec2 describe-availability-zones --region us-east-1 to map AZ names to AZ IDs for your account. Bake the AZ ID (not the name) into your Terraform variable definitions. This single check prevents the most expensive provisioning failure in ODB deployments.

The Bottom Line

Oracle Database@AWS occupies a specific position: it's for enterprises that need the full Oracle Exadata feature set, RAC, Data Guard, smart scan, MAA guarantees, but operate primarily on AWS and can't justify running a separate OCI tenancy for their database tier. It's not cheaper than RDS or EC2. It's not simpler to operate. It's the right answer when the requirements genuinely demand what only Exadata delivers.
