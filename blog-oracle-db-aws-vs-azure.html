Oracle Database@AWS
vs Oracle Database@Azure:
A Practitioner's Comparison

Architecturally identical concepts. Meaningfully different implementations. I've delivered both in production — here's where they diverge in Terraform, networking, commercial model, and which workloads land where.

I'm in a position that's still uncommon: I've delivered Oracle Database@Azure in production (DIPS AS — Norway's national EHR, one of the earliest ODBAA deployments in Northern Europe) and I've built the Terraform module library for Oracle Database@AWS. That combination — hands-on ODBAA production delivery plus AWS module development — is why this comparison exists as a practitioner article rather than a spec-sheet comparison.

The short version: they're architecturally identical at the Oracle level (same Exadata hardware, same database software, same Oracle management plane), and meaningfully different at the provider level. The differences that matter are in Terraform tooling, networking model, key management integration, and commercial structure. The choice between them should be driven by your existing cloud footprint — not by any technical superiority of one over the other.

What's the Same

Both services run genuine Oracle Exadata hardware inside a hyperscaler Availability Zone, managed by Oracle, accessed over a private low-latency network peering from your application VPC or VNet. Both expose the full Oracle Exadata feature set: RAC, Active Data Guard, smart scan, TDE, Oracle MAA. Both are provisioned in two phases — hyperscaler networking and infrastructure, then Oracle database layer via the OCI provider.

If you know how to operate Oracle Exadata, you know how to operate the database layer on both. The DBA experience — AWR, ASM, RAC administration, Data Guard failover — is identical. The hyperscaler wrapper is different; the database is the same.

Terraform Provider Differences

This is where the implementation diverges most significantly for infrastructure engineers.

The AzAPI vs azurerm choice for ODBAA

For Oracle Database@Azure, the storage vault uses azurerm_oracle_exascale_database_storage_vault (now in azurerm), while the VM cluster uses azapi_resource with type Oracle.Database/exadbVmClusters. Use azurerm for standard Azure resources (VNet, Key Vault, subnets) and AzAPI for the cluster resource. Pin the api_version on AzAPI resources — type strings change with API versions and an unpinned resource will drift.

Networking Model

Both use private, low-latency peering between the application network and the Oracle network. The mechanism differs.

On AWS: the ODB network is a dedicated networking construct with its own namespace (aws_odb_network), separate from your VPC. The peering connection (aws_odb_network_peering_connection, prefix odbpcx-) has its own lifecycle — it's not a standard VPC peering resource and doesn't appear in the standard VPC peering console view. Route table updates to point application subnets at the ODB network are required explicitly.

On Azure: ODBAA uses subnet delegation — a specific subnet in your VNet is delegated to Oracle.Database/networkAttachments. The Exadata infrastructure attaches to this delegated subnet. No separate peering construct; the database is addressable from the VNet directly via the delegated subnet's IP space. This is arguably simpler to reason about for Azure-native teams — the database lives in a subnet, like everything else.

Both models achieve the same outcome: sub-millisecond latency between application tier and database, fully private, no public internet traversal.

Key Management

On AWS: TDE wallet keys are managed in AWS KMS. The VM cluster resource references a KMS key ARN at creation time. Key rotation follows standard AWS KMS rotation policies. This is a natural fit for enterprises that already have AWS KMS governance — Oracle TDE keys become first-class citizens in the existing key management model.

On Azure: TDE keys are managed in Azure Key Vault. The ODBAA cluster references a Key Vault URI. Key Vault RBAC and access policies govern TDE key access. Again, a natural fit for Azure-first enterprises — TDE keys live alongside all other secrets and keys in Key Vault, with the same rotation and audit mechanisms.

Both approaches eliminate the need for a standalone Oracle Wallet management process. Choose based on where your existing key management governance lives.

Commercial Model Differences

Both services bill jointly — Oracle charges for database software and managed service; the hyperscaler charges for infrastructure. The billing relationship differs:

  • AWS: ODB charges appear on the AWS bill. May count toward existing AWS EDP commitments (subject to negotiation). Single invoice, AWS Cost Explorer visibility across ODB and all other AWS services.
  • Azure: ODBAA charges appear on the Azure bill. May count toward Azure MACC (Microsoft Azure Consumption Commitment) in some configurations. Azure Cost Management visibility across ODBAA and all other Azure services.

Both support LicenseIncluded and BYOL. The BYOL mechanics — Oracle LMS verification, ULA scope, per-processor vs ECPU mapping — are the same regardless of hyperscaler. The Exadata sizing units differ slightly: AWS uses compute count and CPU core count; Azure uses ECPU (Elastic CPU) in the range 8–200, multiples of 4.

Which to Choose and When

"The choice between ODB@AWS and ODBAA should be driven by your existing cloud footprint. If your application tier is AWS-first, choose ODB. If it's Azure-first, choose ODBAA. Running both because different workloads are on different clouds is a legitimate pattern — it's what the Oracle multicloud strategy is designed to support."

Three scenarios where the answer is clear:

  • Azure-first enterprise running Oracle EBS or JD Edwards: ODBAA. The application tier is in Azure, the DBAs already manage Azure Key Vault, and the Terraform team knows azurerm. ODB would add AWS to an Azure shop for no benefit.
  • AWS-first enterprise with Oracle APEX application in EKS: ODB. Application is in AWS, sub-millisecond Oracle access is required, and the team doesn't want a second cloud relationship. ODBAA would require Azure infrastructure for a purely AWS workload.
  • Enterprise running Oracle on on-premise Exadata, migrating to cloud: whichever hyperscaler the rest of the workload is moving to. Don't let the Oracle database choice drive the hyperscaler selection — let the hyperscaler selection (driven by application, data, and team considerations) drive the Oracle deployment model.
